Agents

What’s an agent?

  • An LLM, in a harness, that calls tools repeatedly in a loop — deciding each next step from the last result

  • Most agents have two kinds of tools: read tools to observe the world, and write tools to change it

This is Hadley Wickham’s definition, from his “What is an agent?” post on Substack.

Simon Willison’s shorter version: an LLM with a read tool and a write tool.

The “you know it when you see it” version: an autonomous system that needs minimal intervention to finish a task.

All three describe the same thing. The loop is what makes it an agent.

One tool call is not an agent

The quiz show called a tool. So why wasn’t it an agent?

No loop, no decisions: the model called the sound tool and answered.

Recall the quiz show app: we registered one tool, and the model called it to play sounds during the game.

Each user message produced at most one tool call before the final answer.

An agent keeps calling tools in a loop, deciding each next step from the result of the last one.

The agent loop

  • Explore: the agent reads to understand the world

  • Act: the agent writes to change it

  • Observe: the agent reads again to see what changed

  • …and repeat until the task is done

The loop is why agents feel different from a chat: the model, not the user, chooses the next step.

The harness (ellmer or chatlas) does the busy work: it runs each tool, sends the result back, and lets the model continue.

Read tools and write tools

Read tools observe Write tools change
Read a file Write a file
List files Edit a file
Search the codebase Run a command
Look at data Run code

Read and write is the smallest split that still makes an agent useful.

A coding agent is just an agent whose tools mirror how a human works on a codebase.

Hadley: “A coding agent is six functions in a trenchcoat” — read file, write file, edit file, list files, search, run command, plus a big system prompt of advice.

What counts as dangerous?

Danger = expensive, time-consuming, or impossible to undo

  • Delete a file outside git

  • Drop a database table

  • Spend money

  • Send an email

  • Leak a secret or personal data

Hadley’s framing from “Help! My coding agent can run code”: dangerous means hard to undo.

Running the renewal script touches only a disposable, local fixture.

Sending a letter leaves the sandbox and reaches a real person.

The store’s no-late-fees settlement is a reminder that careless promises have consequences.

Three ways to keep an agent in check

  1. Ask for permission — but 99% of approvals are safe, so people click yes without reading

  2. Sandbox — the OS constrains the process, but temp folders, package libraries, and network access all leak in

  3. Ask an LLM — run in the sandbox, and when it rejects a call, have an LLM review the code and the conversation

Help! My coding agent can run code

The three approaches, in the order real tools adopted them.

Permission prompts become security theatre. Prefix allowlists fail: git push is safe, git push --force often isn’t.

Sandboxing works but is fiddly: R needs a writable temp dir and a readable library path.

The state of the art is sandbox plus LLM review — which is what Posit Assistant does when it declines to run something risky. Some actions stay off-limits even when you ask for them explicitly.

Agents, recap

  • An agent is an LLM, in a harness, calling tools in a loop

  • Read tools observe; write tools change

  • The harness does the busy work — you write the tools and the system prompt

  • General tools make useful agents, and safety is the price
